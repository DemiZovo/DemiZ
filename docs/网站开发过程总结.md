# DemiZ 个人网站开发过程总结

## 项目背景

DemiZ 个人网站用于整理代码学习笔记、展示 GitHub 项目和记录生活随笔。项目希望在“冷淡、克制、易阅读”的视觉基调上，加入轻量卡片布局，并最终通过 GitHub Pages 持续发布。

网站采用 Astro 构建，主要技术包括 TypeScript、Markdown、Astro Content Collections、GitHub Actions 和 GitHub Pages。开发时优先考虑静态输出、内容维护成本和长期可扩展性，没有引入数据库或复杂的客户端框架。

## 从需求到首版网站

开发开始时，先把需求拆成五个主要栏目：首页、技术博客、代码项目、生活日志和关于我。同时补充了搜索、标签、归档、RSS、Sitemap、深浅色模式、回到顶部、访问统计和 GitHub Pages 部署等基础能力。

首版在 2026 年 8 月 13 日完成，主要工作包括：

- 建立 Astro 与 TypeScript 工程，配置静态站点输出。
- 创建统一的页面布局、顶部导航和页脚。
- 完成首页、博客列表与详情、生活日志、项目、关于、隐私和 404 页面。
- 建立标签页、时间归档、站内搜索索引与 RSS 输出。
- 加入低饱和度配色、卡片样式、响应式布局和深浅色模式。
- 为 GitHub Pages 的仓库子路径准备 URL 处理逻辑。
- 建立自动检查、构建和部署流程。

这一阶段没有把页面写成彼此独立的静态文件，而是先搭建内容模型和公共读取层，再让不同页面消费同一份内容数据。这使后续新增文章时只需要编写 Markdown，不必同步修改首页、列表、标签、归档、搜索和 RSS。

## 内容模型设计

网站使用 Astro Content Collections 管理 `blog` 和 `life` 两类内容，并在 `src/content.config.ts` 中通过 Zod 定义字段约束。

技术博客包含标题、摘要、固定短链接、发布日期、更新日期、分类、标签、封面、草稿、精选和目录开关。生活日志沿用大部分通用字段，并额外提供图集数据。开发中对以下规则进行了明确限制：

- `slug` 只能由英文小写字母、数字和连字符组成。
- 标题与摘要设置长度上限。
- `updated` 不得早于 `published`。
- 图片必须使用受支持的格式。
- 图集图片必须填写替代文字。
- 常用布尔值和数组字段提供默认值。

`src/lib/content.ts` 被设计为公开内容的唯一读取入口。开发环境可以预览草稿，生产构建则统一排除 `draft: true` 的内容。这个边界同时服务于详情页、列表、首页、搜索索引和 RSS，避免某个出口忘记过滤草稿。

公开地址由 frontmatter 中的 `slug` 决定，而不是由 Markdown 文件名决定。这样移动或重命名源文件不会意外改变文章地址，但文章发布后仍应尽量保持 `slug` 稳定。

## 页面与功能实现

首页负责展示个人简介、GitHub 入口以及近期博客和生活内容。博客与生活栏目通过静态路由生成详情页，并共用内容排序和公开状态规则。

标签页从已发布内容的 `tags` 字段自动聚合，无需手工维护标签清单。归档页根据 `published` 按时间倒序和年份分组，`updated` 只用于展示更新时间，不影响归档位置。

站内搜索在构建阶段生成 `search-index.json`，浏览器端对标题、摘要、分类和标签进行实时匹配。查询会统一大小写和 Unicode 形式，并移除空格，以兼顾中英文输入。当前实现没有索引 Markdown 正文，也没有加入模糊纠错或分词服务，换取了更小的运行成本和更简单的部署方式。

项目页采用“本地配置为主、GitHub 数据为增强”的方案。仓库名称、介绍和标签保存在本地；构建时可以补充 Stars、Forks、主要语言和更新时间。即使 GitHub API 不可用，页面仍能依靠本地数据完成构建。当前尚未配置具体项目，因此页面显示空状态和 GitHub 主页入口。

## GitHub Pages 子路径处理

项目部署地址是 `https://demizovo.github.io/DemiZ/`，因此页面不能假设网站始终位于域名根目录。

Astro 配置通过 `SITE_URL` 和 `BASE_PATH` 接收部署环境信息。Markdown 中以 `/` 开头的站内图片和链接会在构建时补上仓库子路径，页面代码则通过统一的 URL 工具生成地址。GitHub Actions 会根据仓库所有者与仓库名计算最终站点地址和 base path，使同一套代码可以兼容用户主页仓库与普通项目仓库。

子路径问题是本项目最容易出现“本地正常、线上失效”的地方，因此构建完成后还会检查生成文件中的内部链接与资源目标，而不是只看 Astro 是否返回成功。

## 自动检查与部署

项目提供三层本地验证：

```bash
npm run check:content
npm run build
npm run verify:build
```

`check:content` 用于同步集合并检查 Astro、TypeScript 和内容字段；`build` 生成正式静态站点；`verify:build` 则继续检查：

- 是否泄漏草稿测试标记。
- 是否残留本机路径、`localhost` 或乱码替换字符。
- 根相对链接是否遗漏 GitHub Pages 子路径。
- HTML 中引用的站内页面和资源是否真实存在。
- 首页、404、关于、隐私、搜索、RSS、搜索索引和 Sitemap 等关键产物是否生成。

GitHub Actions 在推送、拉取请求和手工触发时运行。流程会锁定 Node.js 版本、使用 `npm ci` 安装依赖、执行内容检查与生产构建，再上传并部署 Pages 产物。2026 年 8 月 13 日，首版完成线上部署验收，正式首页、博客、项目、关于页和 RSS 均可访问。

## 访问统计与隐私

网站预留了 Umami 访问统计，但采用显式启用策略。只有部署环境提供 `UMAMI_WEBSITE_ID` 时，工作流才会打开统计并注入对应配置；没有配置时不会加载第三方统计脚本。

统计逻辑独立放在配置和组件中，避免散落到各个页面。启用自托管 Umami 时，也可以通过环境变量替换脚本地址。与此同时，隐私页面为未来启用统计保留了说明入口。

## 内容和维护文档的完善

首版上线后，项目没有继续堆叠页面功能，而是集中完善维护体验。README 逐步补充了本地运行、发布博客、管理草稿、维护标签与归档、使用搜索、插入图片、替换头像、更新个人资料、添加小红书链接、展示 GitHub 项目和发布网站等说明。

在内容方面，示例文章曾根据实际使用需要删除和重新发布；随后加入了 WSL2 学习笔记，并建立了适合本站风格的博客写作规范。最近一次调整更新了站点个人信息和首页文案。这个过程说明网站已经从“能生成页面”的工程骨架，逐渐转向“可以持续记录和维护”的个人内容系统。

## 开发中值得保留的经验

第一，内容过滤规则应该集中管理。草稿若分别在页面、RSS 和搜索中处理，很容易出现遗漏；统一读取层能显著降低风险。

第二，静态站点也需要产物级验证。类型检查和构建成功不能证明链接一定正确，尤其是在 GitHub Pages 子路径场景中。对 `dist` 做二次检查能够提前发现线上 404、资源路径和草稿泄漏问题。

第三，外部数据应作为增强而不是构建前提。GitHub 仓库数据和 Umami 统计都可能受网络或配置影响，本地内容和核心页面不应因此失效。

第四，先设计维护流程，再持续增加内容。Schema、目录约定、README 和写作规范虽然不会直接出现在页面视觉中，却决定了网站能否长期使用。

## 当前状态与后续方向

目前网站已经具备稳定的静态内容发布、分类浏览、搜索、归档、RSS、自动检查和 GitHub Pages 部署能力。后续工作主要是内容与个人化，而不是重做基础架构：

- 替换真实头像并完善个人介绍。
- 在 `src/config/projects.ts` 中加入希望展示的仓库。
- 根据需要启用 Umami，并同步更新隐私说明。
- 持续补充技术文章和生活日志。
- 在内容足够后，再评估相册、代码片段收藏和学习打卡等扩展栏目。

整个开发过程的核心不是一次性完成所有功能，而是建立一套结构清晰、验证可靠、维护成本较低的个人发布流程。现在新增一篇文章或日志，只需要编辑 Markdown、运行检查并推送，后续构建和部署可以自动完成。
